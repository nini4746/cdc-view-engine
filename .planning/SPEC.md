# CDC 실시간 구체화 뷰 엔진 SPEC

작성일: 2026-07-07. 방법론: spec-goal-flow (셀프 인터뷰, 최종 모호성 0.121, 게이트 통과). 1인 개발 전제.

## 개요

PostgreSQL 변경 (Debezium CDC) 을 Kafka Streams로 조인/집계해 항상 최신인 구체화 뷰를 REST API로 제공하는 독립 서버. 뷰는 코드가 아닌 YAML 설정 파일로 선언한다. 데모 도메인은 커머스 (주문 + 재고 + 정산), 산출물은 독립 서버 + docker compose 데모다.

## 핵심 아키텍처 결정 (인터뷰에서 확정)

- 뷰 상태 저장: Kafka Streams state store (RocksDB). 동일 프로세스에서 REST 서빙. 단일 인스턴스 전제.
- 이벤트 순서 기준: Debezium 이벤트의 PG LSN. 같은 키에서 LSN이 작은 이벤트는 폐기 (last-write-wins).
- 윈도우: tumbling + sliding (hopping) 2종. 크기와 grace (기본 30초) 설정 가능. 윈도우는 [start, end) 반개구간.
- 캐시 무효화: 외부 캐시 (Redis 등) 는 범위 외. REST 응답의 ETag + freshness 메타데이터로 대체.
- 재구축 트리거: 수동 REST 엔드포인트. 뷰 미참조 컬럼 추가는 재구축 없이 무중단 통과.
- 대상 테이블은 REPLICA IDENTITY FULL 필수 (UPDATE/DELETE의 before 이미지 확보).

## 경계

### 범위 내

- PostgreSQL 단일 소스 CDC (Debezium, Kafka Connect)
- YAML 뷰 정의: 소스 테이블, 조인 키, 집계 함수 (count/sum/min/max/avg), 윈도우 선언
- Kafka Streams 조인/집계 구체화 + RocksDB state store
- REST 조회 API (키 조회, 윈도우 시간 범위 조회, ETag/freshness)
- 순서 뒤집힌 이벤트 처리 (LSN 기반 + grace + DLQ)
- exactly-once (EOS v2 + LSN 멱등 필터 + 재시작 안전성)
- 정합성 검증기 (소스 스냅샷 대비 뷰 비교, 온디맨드)
- 스키마 변경 중 뷰 재구축 (섀도 빌드 + 원자적 스왑, 무중단)
- 커머스 시뮬레이터 + docker compose 원커맨드 데모
- 벤치마크 하네스 (p95 지연, 처리량 리포트)

### 범위 외 (이유)

- 관리 UI: REST + 설정 파일로 충분, MVP 가치 대비 비용 큼
- 멀티 인스턴스 스케일아웃: 단일 인스턴스로 핵심 난제 4개 증명 가능, interactive query 라우팅은 별도 프로젝트급
- 인증/멀티테넌시: 포트폴리오 데모 용도, 보안 계층은 소비자 (2번 프로젝트) 몫
- 비PG 소스 (MySQL, MongoDB 등): Debezium 커넥터 추상화 비용 대비 서사 이득 없음
- 외부 캐시 (Redis) 자동 무효화: REST ETag로 캐시 검증 가능, 외부 캐시 도입은 소비자 선택
- 뷰 정의 핫 리로드: 뷰 정의 변경은 재구축 절차 (R8) 로만 반영
- 뷰가 참조하는 컬럼의 삭제 지원: MVP는 컬럼 추가 + 뷰 정의 변경만. 참조 컬럼 삭제는 명시적 에러로 거부

## 요구사항

### R1. YAML 뷰 정의

- 반증 가능 문장: 사용자는 서버 코드 수정 없이 YAML 파일 하나로 조인 키, 집계 함수, 윈도우를 선언해 새 뷰를 등록할 수 있다.
- 현재 상태: 없음 (그린필드)
- 목표 상태: `views/*.yaml` 을 부팅 시 로딩/검증해 뷰 레지스트리를 구성. 검증 실패 시 부팅 중단.
- 수용 기준:
  - [ ] AC1-1: 소스 테이블 2개 이상 + 조인 키 + 집계 함수 (count/sum/min/max/avg) + 윈도우 (tumbling/sliding, 크기 + grace) 를 YAML로 선언하면 부팅 시 뷰가 등록된다
  - [ ] AC1-2: 필수 필드 누락 또는 알 수 없는 필드가 있는 YAML은 부팅이 실패하고 (exit code != 0), 에러 메시지에 파일명과 필드 경로가 포함된다
  - [ ] AC1-3: 데모용 커머스 뷰 정의 2개 (주문+재고+정산 조인 집계 뷰 1개, 슬라이딩 윈도우 집계 뷰 1개) 가 저장소에 포함된다

### R2. PostgreSQL CDC 수집

- 반증 가능 문장: 소스 PG 테이블의 INSERT/UPDATE/DELETE 커밋은 Debezium을 거쳐 엔진 내부 이벤트 (before/after, LSN, 커밋 ts_ms 포함) 로 도착한다.
- 현재 상태: 없음
- 목표 상태: 엔진이 뷰 정의에 선언된 테이블 대상 Debezium 커넥터를 자동 등록하고, CDC 토픽을 소비해 내부 이벤트로 파싱.
- 수용 기준:
  - [ ] AC2-1: compose 기동 후 엔진이 뷰 정의에 선언된 테이블에 대한 Debezium 커넥터를 Kafka Connect REST API로 자동 등록한다
  - [ ] AC2-2: 소스 테이블에 INSERT/UPDATE/DELETE를 각각 실행하면, 엔진이 before/after, LSN, 커밋 ts_ms를 파싱한 내부 이벤트를 수신했음을 로그 또는 메트릭으로 확인할 수 있다
  - [ ] AC2-3: REPLICA IDENTITY FULL이 아닌 대상 테이블이 감지되면 커넥터 등록 단계에서 테이블명을 포함한 명시적 에러를 낸다

### R3. 조인/집계 뷰 구체화

- 반증 가능 문장: 뷰 정의에 선언된 조인/집계 결과가 state store에 구체화되고, 소스 변경 커밋마다 자동 갱신된다.
- 현재 상태: 없음
- 목표 상태: 뷰 정의로부터 Kafka Streams 토폴로지 (테이블 조인, 집계, 윈도우 집계) 를 동적으로 구성.
- 수용 기준:
  - [ ] AC3-1: 주문 테이블 INSERT 후 조인 뷰의 해당 키 집계값이 갱신된다
  - [ ] AC3-2: UPDATE 시 sum 집계에서 이전 값이 차감되고 새 값이 가산된다 (old 기여분 제거 검증)
  - [ ] AC3-3: DELETE 시 해당 행의 기여분이 집계에서 제거된다
  - [ ] AC3-4: 윈도우 집계는 [start, end) 반개구간 규칙을 따른다 - 윈도우 종료 시각과 정확히 같은 event time의 이벤트는 다음 윈도우에 속한다

### R4. REST 조회 API

- 반증 가능 문장: 클라이언트는 REST로 뷰의 최신 값과 freshness 메타데이터를 조회할 수 있다.
- 현재 상태: 없음
- 목표 상태: 키 조회 + 윈도우 범위 조회 엔드포인트, ETag 지원.
- 수용 기준:
  - [ ] AC4-1: GET /views/{view}/{key} 가 최신 집계값과 freshness 메타 (마지막 반영 이벤트의 커밋 ts_ms, 뷰 반영 시각) 를 JSON으로 반환한다
  - [ ] AC4-2: 윈도우 뷰는 GET /views/{view}/{key}?from={ts}&to={ts} 로 시간 범위 내 윈도우 결과 목록을 반환한다
  - [ ] AC4-3: 존재하지 않는 키 또는 뷰는 404와 에러 바디 (뷰명/키 명시) 를 반환한다
  - [ ] AC4-4: 응답에 ETag (뷰 버전 + 마지막 반영 오프셋 기반) 가 포함되고, If-None-Match 일치 시 304를 반환한다

### R5. 순서 뒤집힌 이벤트 처리

- 반증 가능 문장: 같은 키의 이벤트가 커밋 순서와 다르게 도착해도, 최종 뷰 값은 LSN 순서대로 처리한 결과와 같다.
- 현재 상태: 없음
- 목표 상태: 키별 LSN 비교 기반 stale 이벤트 폐기, 윈도우 grace 내 지각 이벤트 반영, grace 초과분 DLQ.
- 수용 기준:
  - [ ] AC5-1: 테스트 하네스로 같은 키의 UPDATE 2건을 역순 주입하면, 뷰 값은 LSN이 큰 이벤트 기준이다
  - [ ] AC5-2: DELETE가 UPDATE보다 먼저 도착하는 역순 시나리오에서, 최종 뷰에 해당 행이 되살아나지 않는다
  - [ ] AC5-3: 윈도우 집계에서 grace (기본 30초, 뷰 정의로 설정 가능) 이내 지각 이벤트는 해당 윈도우 결과에 반영된다
  - [ ] AC5-4 (N3): grace 초과 지각 이벤트는 뷰에 반영하지 않되, DLQ 토픽에 적재되고 late-event 카운터 메트릭이 증가한다 - 흔적 없는 폐기 금지

### R6. exactly-once

- 반증 가능 문장: 이벤트 중복 전달과 엔진 비정상 종료/재시작 상황에서도 뷰 집계값은 각 커밋을 정확히 한 번 반영한 값과 같다.
- 현재 상태: 없음
- 목표 상태: Kafka Streams EOS v2 + LSN 기반 멱등 필터 (Debezium→Kafka 구간의 at-least-once 중복 방어).
- 수용 기준:
  - [ ] AC6-1: Kafka Streams processing.guarantee=exactly_once_v2 가 활성화되어 있다 (설정 검증 테스트)
  - [ ] AC6-2 (N1): 동일 LSN 이벤트를 CDC 토픽에 2회 주입해도 sum/count 값이 변하지 않는다 - 동일 커밋이 집계에 2회 반영되는 일은 어떤 경로로도 없어야 한다
  - [ ] AC6-3: 처리 도중 엔진 프로세스를 kill -9 하고 재시작한 뒤, 최종 뷰 값이 무중단 실행 시의 기대값과 동일하다
  - [ ] AC6-4: 위 재시작 시나리오가 자동화 스크립트로 저장소에 포함되어 반복 실행 가능하다

### R7. 정합성 검증기

- 반증 가능 문장: 검증기는 소스 PG 스냅샷으로 계산한 기대 뷰와 서빙 중인 뷰를 비교해 불일치 수를 리포트한다.
- 현재 상태: 없음
- 목표 상태: 온디맨드 REST 트리거 검증, quiesce 조건에서 pass/fail 판정.
- 수용 기준:
  - [ ] AC7-1: POST /admin/verify/{view} 호출 시 소스 테이블 스냅샷 기반 기대값을 계산해 뷰와 비교하고, 불일치 키 수 + 불일치 샘플 (최대 10건) 리포트를 반환한다
  - [ ] AC7-2: quiesce 조건 (시뮬레이터 정지 + consumer lag 0) 에서 데모 시나리오 10만 이벤트 처리 후 검증 결과 불일치 0건이다
  - [ ] AC7-3: 스트림이 흐르는 중 실행하면 결과에 non-quiesced 플래그가 표시되고 pass/fail 판정은 하지 않는다
  - [ ] AC7-4 (N4): 검증 실행 중에도 뷰 REST 조회가 계속 200으로 응답한다 - 검증이 서빙을 블로킹하지 않는다

### R8. 스키마 변경 중 뷰 재구축

- 반증 가능 문장: 소스 스키마 변경 (컬럼 추가) 과 뷰 정의 변경 시, 기존 뷰 서빙을 중단하지 않고 뷰를 재구축해 원자적으로 교체할 수 있다.
- 현재 상태: 없음
- 목표 상태: 스냅샷 기반 섀도 뷰 빌드 + 원자적 스왑, 재구축 중 신규 이벤트 무유실, 멱등 재시도.
- 수용 기준:
  - [ ] AC8-1: 뷰가 참조하지 않는 컬럼을 ALTER TABLE ADD COLUMN 한 뒤에도 CDC 처리와 뷰 갱신이 에러 없이 지속된다
  - [ ] AC8-2: 뷰 정의 변경 후 POST /admin/views/{view}/rebuild 를 호출하면 소스 스냅샷부터 섀도 뷰를 재구축하고 완료 시 원자적으로 스왑한다
  - [ ] AC8-3 (N2): 재구축 진행 중과 스왑 시점에 REST 조회는 기존 (또는 스왑 후 신규) 뷰의 완결된 값만 반환한다 - 재구축 시작부터 스왑 완료까지 조회 루프에서 5xx/빈 응답/신구 혼합 응답 0건
  - [ ] AC8-4: 재구축 중 발생한 신규 CDC 이벤트가 스왑 후 뷰에 반영되어 있다 - 스왑 후 정합성 검증기 결과 불일치 0건
  - [ ] AC8-5: 뷰가 참조하는 컬럼이 소스에서 삭제된 상태로 재구축을 요청하면, 검증 단계에서 컬럼명을 포함한 명시적 에러로 거부한다
  - [ ] AC8-6: 재구축 도중 엔진을 재시작해도 기존 뷰 서빙이 유지되고, 재구축을 다시 요청하면 정상 완료된다 (멱등)

### R9. 지연/처리량 목표

- 반증 가능 문장: 기준 환경에서 초당 1만 이벤트 부하 하에 DB 커밋 → REST 조회 반영 지연 p95가 1초 이내다.
- 현재 상태: 없음
- 목표 상태: 커밋 ts_ms 대비 뷰 반영 시각으로 지연 분포를 산출하는 벤치 하네스 + 목표 달성 리포트.
- 수용 기준:
  - [ ] AC9-1: 벤치 하네스가 Debezium 커밋 ts_ms와 뷰 반영 시각의 차이로 지연 분포 (p50/p95/p99) 를 산출해 리포트 파일을 생성한다
  - [ ] AC9-2: 시뮬레이터 10,000 events/sec, 10분 지속, 워밍업 60초 제외 조건에서 p95 ≤ 1,000ms 다
  - [ ] AC9-3: 리포트에 실행 하드웨어 사양 (CPU, 메모리, docker 리소스 한도) 이 기록된다
  - [ ] AC9-4: 부하 중 처리 실패와 DLQ 오적재가 0건이다 (의도적으로 주입한 순서 역전 케이스 제외)

### R10. docker compose 원커맨드 데모

- 반증 가능 문장: docker compose up 한 번으로 전체 데모 스택 (PG + Kafka + Debezium + 엔진 + 시뮬레이터) 이 구동되고 커머스 뷰를 REST로 조회할 수 있다.
- 현재 상태: 없음
- 목표 상태: 원커맨드 재현 가능 데모.
- 수용 기준:
  - [ ] AC10-1: docker compose up 으로 PG, Kafka, Kafka Connect (Debezium), 엔진 컨테이너가 모두 healthy 상태에 도달한다
  - [ ] AC10-2: 엔진 헬스 엔드포인트 (actuator health) 가 200을 반환한다
  - [ ] AC10-3: 커머스 시뮬레이터가 compose로 함께 구동되어 주문/재고/정산 데이터를 설정 가능한 속도 (events/sec) 로 생성한다
  - [ ] AC10-4: compose up 후 5분 내 수동 개입 없이 판매자 대시보드 뷰의 REST 조회가 실데이터를 반환한다
  - [ ] AC10-5: README에 기재된 데모 절차 (명령어 3개 이하) 를 그대로 따라 재현 가능하다

## 부정 수용 기준 (must-NOT)

각 항목은 위 요구사항의 AC에 귀속되어 있다 (중복 판정 방지).

- N1: 동일 커밋 (LSN) 이 어떤 경로로도 집계에 2회 반영되지 않는다 → AC6-2
- N2: 재구축 스왑 시점에 API가 빈 결과나 신/구 뷰가 섞인 결과를 반환하지 않는다 → AC8-3
- N3: grace 초과 지각 이벤트가 흔적 없이 폐기되지 않는다 (DLQ + 메트릭 필수) → AC5-4
- N4: 정합성 검증이 뷰 서빙을 블로킹하지 않는다 → AC7-4

## 엣지 프로브 결정 기록

| 엣지 | 결정 | 반영 |
|---|---|---|
| 같은 키 UPDATE 2건 역순 도착 | 명세에 추가 | AC5-1 |
| DELETE가 UPDATE보다 먼저 도착 (행 부활 위험) | 명세에 추가 | AC5-2 |
| 윈도우 종료 시각과 정확히 같은 event time | 명세에 추가 ([start, end) 반개구간) | AC3-4 |
| 처리 도중 kill -9 후 재시작 | 명세에 추가 | AC6-3 |
| 검증 중 스트림이 흐르는 경우 | 명세에 추가 (non-quiesced 플래그) | AC7-3 |
| 뷰 참조 컬럼 삭제 | 기각 - MVP는 컬럼 추가 + 뷰 정의 변경만. 삭제는 명시적 에러로 거부 | AC8-5, 경계 섹션 |
| UPDATE/DELETE before 이미지 누락 (TOAST 등) | 명세에 추가 (REPLICA IDENTITY FULL 강제) | AC2-3 |
| 콜드 스타트 직후 지연 스파이크 | 명세에 추가 (워밍업 60초 제외) | AC9-2 |
