## 하네스 결함 (수정)

1. **percentile 파싱 실패**: `view.apply.latency`가 `publishPercentileHistogram()`으로 노출되면서 Micrometer `quantile=` 요약 라인이 나오지 않음 → 스크립트가 p95를 못 읽어 전부 `?` → 잘못된 FAIL. 누적 버킷(`_bucket{le=...}`)에서 백분위를 계산하도록 교체.
2. **워밍업 미제외**: 누적 히스토그램은 감쇠하지 않아 워밍업/백로그가 그대로 섞임. [측정 시작, 측정 종료] 두 시점 버킷 스냅샷을 차분(delta)해 워밍업 제외 정상상태 분포를 산출하도록 수정. 구간 내 순시 consumer lag 도 스크레이프에 추가 (정상상태 판별).
3. verdict 방어: p95가 `>30000`(문자열)이거나 빈 값이면 PASS 오판 방지.

## 시뮬레이터 결함 (수정)

- deficit 배치 상한 `maxBatch`가 `rate` 전량(1초 분량)이라, 10,000/s에서 단일 트랜잭션에 최대 1만 행을 커밋 → 수천 행이 동일 커밋 ts를 공유해 지연 측정 왜곡 + PG 부하 스파이크. 절대 상한 500행으로 제한 (고rate에서 여러 루프에 걸쳐 따라잡음, 커밋 잘게 쪼갬).

## 원인 분석 (호스트 리소스 vs 엔진 병목 구분)

두 개의 독립된 병목이 있고, **둘 다 엔진 알고리즘 결함이 아니다**:

1. **처리량 포화 (호스트 리소스 한계)**: 10,000/s에서 lag가 213k까지 폭증 → 8코어를 5개 컨테이너가 공유 + Kafka Streams 단일 스레드 + EOS v2(트랜잭션 오버헤드)의 단일 노드 처리량 한계. 부하 종료 후 정상 배수되므로 영구 고장은 아님. 지속 가능 처리량 상한은 ~2,000/s (lag bounded).

2. **지연 고정 바닥 (파이프라인 config)**: p50가 rate 1,000~2,000/s에서 **716ms로 고정** (백로그와 무관). p95 ≈ 1,074ms. 즉 p95 ≤ 1s 를 막는 건 처리량이 아니라 파이프라인 고정 지연. 가장 유력한 원인은 Debezium `poll.interval.ms`(기본 500ms) + Kafka Streams `commit.interval.ms`(100ms) + Kafka 왕복. **미검증 가설** (본 V3에서 config 실험은 안 함 - 검증 plan 범위).

결론: 목표(10,000/s, p95≤1s)는 이 하드웨어 + 현재 config 에서 미달. 수치를 위조하지 않고 실측 그대로 기록. 엔진의 조인/집계 알고리즘 자체의 병목은 관측되지 않았다 (지연 바닥은 CDC 파이프라인 config, 처리량 한계는 단일 노드/단일 스레드).

## 후속 튜닝 항목 (별도 plan, 수정하지 않고 목록화)

- T1 (지연 바닥): Debezium `poll.interval.ms` 500→50, `max.batch.size` 조정으로 p95 바닥을 ~수백 ms 낮출 여지. commit.interval.ms 100→더 낮추면 EOS 처리량과 트레이드오프.
- T2 (처리량): num.stream.threads 증대 + 입력 토픽 파티션 증가 (현재 1) → co-partitioning 재설계 필요. 또는 멀티 인스턴스 (SPEC 범위 외).
- T3: 벤치 전용으로 컨테이너 리소스 격리(cpuset) 시 co-location 경합 제거 효과 측정.
- T1 검증 실험 (poll.interval 낮춰 p50 바닥 하락 확인) 으로 지연 원인 가설 확정 권장.
